# Can a cheap visibility check decide when to use the other camera?

Opposite-side patch fusion helped occluded pixels but lost more correct pixels elsewhere. On two new panels, use a single untuned rule. Match a point into the first translated image. Match that predicted point back to the reference with the same 3×3 patch rule and the inverse camera displacement. If the round trip misses the starting column, try the opposite camera and use its single-view depth prediction. Otherwise retain the first prediction. Compare that route with always using the first camera, always using both via minimum patch cost, and a randomly selected set of pixels of exactly the same size per world using the opposite camera. Report total and newly visible gains and losses and the proportion routed. Round-trip checking itself costs a second patch search; the fraction routed measures use of the opposite view, not a claim about total latency. Do not use the renderer's visibility labels for prediction. Score two independent 512-layout panels at displacement two and one, seeds 781341 and 1043921, reporting bootstrap intervals over whole layout quartets. Promote only if aggregate accuracy improves over the first camera and matched-budget random replacement, with positive paired lower bounds against both at both baselines. Do not tune a threshold after this comparison.
